### BR-002 — Dockerfile.base: pinned base image with all shared tools
**Priority**: HIGH
**Phase**: build-runner / images
**Depends on**: BR-001 (repo must exist)
**Branch**: `features/BR-002-dockerfile-base`

**Context**:
This is the root of the image hierarchy. Every language-specific image inherits FROM this.
Getting tool versions pinned correctly here avoids breakage in all downstream images.

**Spec**:
Write `Dockerfile.base` in full. Requirements:

1. Base OS: `debian:bookworm-slim` (pinned to a specific digest or at minimum `debian:12.x` — no `latest`).

2. Tools to install via `apt-get` (pin exact package versions where apt allows; at minimum pin the apt-get call to a single RUN layer with `--no-install-recommends` and `apt-get clean`):
   - `curl`
   - `jq`
   - `zip`
   - `unzip`
   - `bash`
   - `git`
   - `ca-certificates`
   - `gnupg`

3. `glab` CLI (GitLab CLI):
   - Install from the official GitLab release: `https://gitlab.com/gitlab-org/cli/-/releases`
   - Pin to a specific version (e.g., `GLAB_VERSION=1.46.0` as an ARG)
   - Download the Linux amd64 binary, verify it runs (`glab --version`)

4. `gh` CLI (GitHub CLI):
   - Install from the official GitHub release: `https://github.com/cli/cli/releases`
   - Pin to a specific version (e.g., `GH_VERSION=2.65.0` as an ARG)
   - Download the Linux amd64 `.deb` or binary, verify it runs (`gh --version`)

5. `node` + `npm`:
   - Install from NodeSource. Pin to Node LTS major version (e.g., Node 22.x as of 2026).
   - Use the NodeSource setup script pinned to a specific Node major: `NODE_MAJOR=22`
   - Verify: `node --version`, `npm --version`

6. `netlify-cli`:
   - Install via `npm install -g netlify-cli@<pinned_version>`
   - Pin version (e.g., `netlify-cli@17.x` — check current stable as of 2026-05)
   - Verify: `netlify --version`

7. Final image hygiene:
   - Single `RUN` layer per logical group (apt install, glab install, gh install, node install, netlify install)
   - `rm -rf /var/lib/apt/lists/*` after apt
   - Non-root user not required (CI runners typically run as root)
   - `WORKDIR /workspace`
   - No `ENTRYPOINT` or `CMD` (parent images should not impose these)

8. Build ARGs to expose at the top of the file (all with pinned defaults):
   ```dockerfile
   ARG DEBIAN_VERSION=12
   ARG GLAB_VERSION=1.46.0
   ARG GH_VERSION=2.65.0
   ARG NODE_MAJOR=22
   ARG NETLIFY_CLI_VERSION=17.x.x   # engineer fills in exact version
   ```

**Acceptance criteria**:

- [ ] `docker run --rm build-runner:base curl --version` exits 0
- [ ] `docker run --rm build-runner:base glab --version` exits 0

   - Verify: `go version`

3. Cross-compile verification (run as part of build, or document as a test command):
   - The image should be able to produce all five platform binaries when given a Go source tree
   - Document in a comment the exact `go build` invocations for each target:

     ```
     GOOS=linux   GOARCH=amd64   CGO_ENABLED=0 go build ...
     ```

### BR-006 — templates/pipeline.yml: shared CI pipeline template
**Priority**: HIGH
**Phase**: build-runner / templates
**Depends on**: BR-002, BR-003 (image tags must be decided before the template references them)
**Branch**: `features/BR-006-pipeline-template`

**Context**:
This is the core deliverable that consuming projects use. They include this file via:
```yaml
include:
  - project: devtrack3_cloud/build-runner
    file: templates/pipeline.yml
```
The template must define three jobs that are self-contained and parameterisable via variables
the consuming project sets.

**Spec**:
Write `templates/pipeline.yml` in full. Requirements:

1. Standard variables block (all overridable by the consuming project):
   ```yaml
   variables:
     BUILD_IMAGE: registry.gitlab.com/devtrack3_cloud/build-runner:base
     PROJECT: $CI_PROJECT_NAME
     VERSION: $CI_COMMIT_TAG
     OUTPUT_DIR: /workspace/bin
   ```

2. Job: `build-dev`
   - `stage: build`
   - Trigger rule: runs on push to `dev` branch only (`rules: - if: '$CI_COMMIT_BRANCH == "dev"'`)
   - Image: `$BUILD_IMAGE`
   - Tags: `[self-hosted]`
   - Script:
     ```yaml
     script:
       - export VERSION=${CI_COMMIT_TAG:-dev}
       - mkdir -p $OUTPUT_DIR
       - bash scripts/build.sh
     ```
   - Artifacts: path `$OUTPUT_DIR/**/*`, expire `1 day`
   - The `$OUTPUT_DIR` is also volume-mounted to the host by the runner config (set in BR-008) so binaries appear locally even after the job container exits

3. Job: `test`
   - `stage: test`
   - Trigger rule: runs on push to any branch AND on `v*` tags (runs before release)
   - `allow_failure: false`
   - Image: `$BUILD_IMAGE`
   - Tags: `[self-hosted]`
   - Script:
     ```yaml
     script:
       - |
         if [ -f scripts/test.sh ]; then
           bash scripts/test.sh
         else
           echo "No scripts/test.sh found — skipping test stage"
         fi
     ```
   - This makes the test job optional for projects that have no test script

4. Job: `release`
   - `stage: release`
   - Trigger rule: runs ONLY on `v*` tags pushed to `main`
     ```yaml
     rules:
       - if: '$CI_COMMIT_TAG =~ /^v/ && $CI_COMMIT_BRANCH == "main"'
     ```
     Note: tags do not have a `CI_COMMIT_BRANCH` set — use:
     ```yaml
     rules:
       - if: '$CI_COMMIT_TAG =~ /^v/'
     ```
   - Image: `$BUILD_IMAGE`
   - Tags: `[self-hosted]`
   - Script:
     ```yaml
     script:
       - export VERSION=$CI_COMMIT_TAG
       - mkdir -p $OUTPUT_DIR
       - bash scripts/build.sh
       - bash scripts/release.sh
     ```
   - Secrets needed (injected by runner or project CI variables):
     - `GLAB_TOKEN` — for `glab release create`
     - `NETLIFY_AUTH_TOKEN` — optional, for projects that deploy a site
   - These are referenced as env vars in the script; the template does not define them (the consuming project or runner provides them)

5. Stage ordering at the top of the file:
   ```yaml
   stages:
     - build
     - test
     - release
   ```

6. Add a file header comment block explaining:
   - How to include this template
   - What variables to set
   - What scripts the consuming project must provide
   - The two-tier workflow (dev push vs tag-on-main)

**Acceptance criteria**:

### BR-007 — .gitlab-ci.yml + scripts/publish.sh: the repo's own CI (builds and publishes images)
**Priority**: HIGH
**Phase**: build-runner / repo CI
**Depends on**: BR-002, BR-003, BR-004, BR-005 (all Dockerfiles must be written before publish can reference them)
**Branch**: `features/BR-007-publish-pipeline`

**Context**:
The build-runner repo must publish its own Docker images when a new version tag is pushed.
This is the "bootstrapping" CI: the repo uses itself (via a temporarily hosted runner or a
one-time manual publish) to publish its images, after which all future builds run on the
self-hosted runner.

For the initial bootstrap, the `.gitlab-ci.yml` in this repo uses GitLab-hosted runners ONLY
for image publishing (a controlled, infrequent operation). After images are published, the
consuming-project pipelines all run on self-hosted runners.

**Spec**:

File 1: `scripts/publish.sh`
This script is called by the CI job to build and push all images to the registry.

```bash
#!/usr/bin/env bash
set -euo pipefail

REGISTRY="registry.gitlab.com/devtrack3_cloud/build-runner"
TAG=${VERSION:-latest}

echo "Publishing build-runner images at tag: $TAG"

# Base image
docker build -f Dockerfile.base -t "$REGISTRY:base-$TAG" -t "$REGISTRY:base" .
docker push "$REGISTRY:base-$TAG"
docker push "$REGISTRY:base"

# Go image
docker build -f Dockerfile.go -t "$REGISTRY:go-$GO_VERSION-$TAG" -t "$REGISTRY:go-$GO_VERSION" .
docker push "$REGISTRY:go-$GO_VERSION-$TAG"
docker push "$REGISTRY:go-$GO_VERSION"

# Python image
docker build -f Dockerfile.python -t "$REGISTRY:python-$PYTHON_VERSION-$TAG" -t "$REGISTRY:python-$PYTHON_VERSION" .
docker push "$REGISTRY:python-$PYTHON_VERSION-$TAG"
docker push "$REGISTRY:python-$PYTHON_VERSION"

# Node image
docker build -f Dockerfile.node -t "$REGISTRY:node-$NODE_MAJOR-$TAG" -t "$REGISTRY:node-$NODE_MAJOR" .
docker push "$REGISTRY:node-$NODE_MAJOR-$TAG"
docker push "$REGISTRY:node-$NODE_MAJOR"

echo "All images published successfully."
```

Required env vars: `VERSION`, `GO_VERSION`, `PYTHON_VERSION`, `NODE_MAJOR` (all set by CI job).

File 2: `.gitlab-ci.yml` (the repo's own pipeline)

```yaml
stages:
  - lint
  - publish

variables:
  GO_VERSION: "1.22"
  PYTHON_VERSION: "3.11"
  NODE_MAJOR: "22"
  DOCKER_DRIVER: overlay2

lint-dockerfiles:
  stage: lint
  image: hadolint/hadolint:latest-debian
  script:
    - hadolint Dockerfile.base Dockerfile.go Dockerfile.python Dockerfile.node
  rules:
    - if: '$CI_COMMIT_BRANCH'  # runs on all branch pushes

publish-images:
  stage: publish
  image: docker:27
  services:
    - docker:27-dind
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
  script:
    - export VERSION=$CI_COMMIT_TAG
    - bash scripts/publish.sh
  rules:
    - if: '$CI_COMMIT_TAG =~ /^v/'  # only on version tags
  tags:
    - docker   # can run on GitLab-hosted runner since this is infrequent
```

Notes:
- `hadolint` is the standard Dockerfile linter — catches common mistakes (no `latest`, shell
  quoting, layer ordering). Install via the `hadolint/hadolint` Docker image.
- The `publish-images` job uses `docker:dind` because it needs to run `docker build` and
  `docker push`. This is one of the rare jobs that intentionally uses GitLab-hosted runners
  (image publishing is infrequent — once per release tag).
- `CI_REGISTRY_USER`, `CI_REGISTRY_PASSWORD`, `CI_REGISTRY` are standard GitLab CI variables,
  auto-populated when the pipeline has access to the Container Registry.

**Acceptance criteria**:
- [ ] `scripts/publish.sh` is executable (`chmod +x`)
- [ ] `publish.sh` builds and tags all four images (base, go, python, node)
- [ ] `publish.sh` pushes both a version-pinned tag AND a language-version tag (e.g., `go-1.22-v1.0.0` AND `go-1.22`)
- [ ] `.gitlab-ci.yml` has a `lint-dockerfiles` job using `hadolint`
- [ ] `.gitlab-ci.yml` has a `publish-images` job triggering only on `v*` tags
- [ ] `.gitlab-ci.yml` is valid YAML
- [ ] `publish.sh` has no hardcoded registry path strings outside the `REGISTRY` variable
- [ ] `scripts/publish.sh` has a usage comment block at the top

### BR-008 — scripts/setup-runner.sh: self-hosted GitLab runner registration
**Priority**: HIGH
**Phase**: build-runner / runner setup
**Depends on**: BR-001 (needs repo structure), BR-002 (runner runs images from this repo)
**Branch**: `features/BR-008-setup-runner`

**Context**:
The self-hosted runner runs as a Docker container on the developer's laptop. It uses the
`docker` executor so each CI job runs in a fresh container pulled from the build-runner
registry. A local `/releases/` volume is mounted into each job container so build artifacts
are accessible on the host after the job finishes.

The developer will run `setup-runner.sh` once to register the runner with GitLab. After that,
the runner container just needs to be started (`docker run gitlab/gitlab-runner run`) whenever
builds are needed.

**Spec**:
Write `scripts/setup-runner.sh` in full. Requirements:

1. Script preamble:
   ```bash
   #!/usr/bin/env bash
   set -euo pipefail
   # setup-runner.sh — Register a self-hosted GitLab runner on your local machine.
   # Prerequisites:
   #   - Docker installed and running
   #   - GITLAB_RUNNER_TOKEN set in environment (from GitLab project Settings > CI/CD > Runners)
   #   - GITLAB_URL set (default: https://gitlab.com)
   # Usage: bash scripts/setup-runner.sh
   ```

2. Validate required env vars (`GITLAB_RUNNER_TOKEN` must be set; error if not).

3. Set sensible defaults:
   ```bash
   GITLAB_URL=${GITLAB_URL:-https://gitlab.com}
   RUNNER_NAME=${RUNNER_NAME:-devtrack-local-runner}
   RELEASES_DIR=${RELEASES_DIR:-$HOME/releases}
   RUNNER_CONFIG_DIR=${RUNNER_CONFIG_DIR:-$HOME/.gitlab-runner}
   ```

4. Create local directories:
   ```bash
   mkdir -p "$RELEASES_DIR"
   mkdir -p "$RUNNER_CONFIG_DIR"
   ```

5. Pull the official gitlab-runner image (pinned version):
   ```bash
   GITLAB_RUNNER_IMAGE="gitlab/gitlab-runner:v17.x.x"  # engineer fills in current stable
   docker pull "$GITLAB_RUNNER_IMAGE"
   ```

6. Register the runner:
   ```bash
   docker run --rm \
     -v "$RUNNER_CONFIG_DIR:/etc/gitlab-runner" \
     "$GITLAB_RUNNER_IMAGE" register \
       --non-interactive \
       --url "$GITLAB_URL" \
       --token "$GITLAB_RUNNER_TOKEN" \
       --executor docker \
       --docker-image "registry.gitlab.com/devtrack3_cloud/build-runner:base" \
       --docker-volumes "/var/run/docker.sock:/var/run/docker.sock" \
       --docker-volumes "$RELEASES_DIR:/workspace/bin" \
       --description "$RUNNER_NAME" \
       --tag-list "self-hosted,docker" \
       --run-untagged false \
       --locked false
   ```

   Key config choices:
   - `--docker-volumes "$RELEASES_DIR:/workspace/bin"` — this is what makes artifacts visible on the host. The `$OUTPUT_DIR` in the pipeline template is `/workspace/bin`, which maps to `$RELEASES_DIR` on the host.
   - `--docker-volumes "/var/run/docker.sock:/var/run/docker.sock"` — allows jobs that need Docker-in-Docker (not needed for build jobs, but useful for flexibility).
   - `--tag-list "self-hosted,docker"` — matches the `tags: [self-hosted]` in the pipeline template.
   - `--run-untagged false` — runner ONLY picks up jobs tagged `self-hosted`; ignores all GitLab-hosted-runner jobs.

7. After registration, print a start command for the developer:
   ```bash
   echo ""
   echo "Runner registered successfully."
   echo ""
   echo "To start the runner:"
   echo "  docker run -d --name gitlab-runner --restart always \\"
   ```
