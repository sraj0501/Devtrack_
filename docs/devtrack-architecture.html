DevTrack

A developer automation platform that observes Git activity, applies AI enrichment, and routes work context to project management systems — automatically, with zero workflow changes for the developer.

Client Go 1.22+ · single binary Server Python 3.12 · FastAPI Boundary HTTPS / JSON only Version v3.0.0 Status Production

1 Executive Summary

DevTrack is a two-component platform. A Go binary runs on the developer's machine and watches Git activity. A Python server runs the AI pipeline: it enriches commit messages, parses work updates using natural language, syncs results to Azure DevOps, GitHub, GitLab, or Jira, and serves a web admin console.

The two components communicate exclusively over HTTPS with a defined JSON contract. They share no code, no database, and no compiled artefact. This clean separation means each can be deployed, scaled, and replaced independently.

2 Problem Statement

Engineering teams routinely lose 30–60 minutes per developer per day to administrative overhead: writing commit messages, updating tickets, filling in standup notes, tracking time. Most of this information already exists in the Git history — it just is not being read.

Existing solutions fall short

  • PM platform integrations (GitHub Apps, Azure DevOps extensions) — require adopting a specific platform, live in the cloud, and still require manual developer input.
  • Time-tracking tools (Toggl, Harvest, Jira Tempo) — require active engagement, creating the same overhead they claim to remove.

DevTrack takes a fundamentally different approach: observe what developers are already doing and use AI to derive work context automatically. No new workflows. No new habits. No mandatory cloud dependency.

💡

Key differentiator: DevTrack runs entirely locally. All AI processing can happen on-device using Ollama. No developer data leaves the machine unless explicitly configured to do so — a critical advantage for enterprises with data residency or compliance requirements.

5 The Python Server

A FastAPI application handling the AI-heavy side of the pipeline. Intentionally separate from the Go client so that LLM providers, PM API clients, and AI models can be updated independently of the binary deployed to developer machines.

Graceful degradation — the core design principle

Every optional subsystem is imported inside a try/except ImportError block. If spaCy is not installed, the LLM handles all text parsing. If ChromaDB is absent, personalization RAG is disabled. If Telegram credentials are missing, the bot simply does not start. A minimal deployment still processes triggers, syncs to PM platforms, and serves the admin console — with no errors at startup.

Personalization — Talk Like You

DevTrack learns how each developer writes. It collects communication samples from Microsoft Teams via MS Graph API, builds a style profile (formality, length, tone, common phrases), and injects that profile into every LLM prompt. The result: AI-generated commit messages and work updates that sound like the developer wrote them — not a generic AI.

RAG (Retrieval-Augmented Generation) using ChromaDB and nomic-embed-text retrieves the most semantically similar examples from the developer's past writing and adds them as few-shot examples. This is significantly more effective than abstract style descriptions alone.

The Boardroom

Seven AI personas — Architect, Security Engineer, Product Manager, Devil's Advocate, Software Engineer, Business Analyst, Scalability Expert — independently review any plan or problem statement. Each produces structured PROs/CONs. The session synthesizes a SWOT matrix and a final verdict. An optional interactive chat mode lets the user interrogate any persona directly.

9 Observability

DevTrack uses runtime-narrative for structured observability. One JSON event is emitted per request stage. Each event carries a story name, stage name, duration, and — on failure — an AI-generated diagnosis from a local LLM.

EventWhen emittedContains
StoryStartedRequest beginsstory name, correlation ID, timestamp
StageCompletedEach pipeline stage finishesstage name, duration_ms, result summary
FailureOccurredAny exceptionerror type, message, LLM diagnosis, suggested fix
StoryCompletedRequest endstotal duration_ms, stage count, outcome

What this enables today

  • Stream live events: tail -f Data/logs/narrative.log | python -m json.tool
  • Console renderer in dev mode: NARRATIVE_RENDERER=console
  • LLM-powered failure diagnosis: when an exception occurs, OllamaFailureAnalyzer queries a small local model and appends a fix suggestion to the log event
  • Admin console: live trigger stats, process health, LLM status panels

Enterprise observability path

The JSON log format is directly ingestible by any log aggregation stack — Elasticsearch, Grafana Loki, CloudWatch, Splunk. The roadmap adds an OpenTelemetry exporter so traces flow into Grafana Tempo, Jaeger, or DataDog with no application code changes. Prometheus /metrics endpoint is also on the roadmap for SLO tracking.

11 Enterprise Scalability Challenges

The current architecture works well for individual developers and small teams. Three issues emerge at enterprise scale.

Problem 1 — Ack latency coupled to processing time

When the Go client sends a trigger, FastAPI processes NLP, runs LLM inference, and calls PM APIs inline before returning a response. If Ollama takes 45 seconds, the Go client waits 45 seconds. At enterprise scale — hundreds of commits per hour from a team — this creates a queue of blocked HTTP connections and unpredictable tail latency.

Problem 2 — One process pays for everything

A single Python process loads spaCy (50MB model), ChromaDB (100MB+ embeddings), every LLM client SDK, the Telegram bot, Slack bot, admin console, and alert poller simultaneously. A team that only uses GitHub sync still pays the memory cost of the entire monolith. Current baseline: 350–500MB per instance.

Problem 3 — CPU-bound work inside the async event loop

spaCy text parsing is CPU-bound. Running it inside an async FastAPI handler blocks the event loop for all other requests during that time. The fix is not more threads — it is a separate process.

Current vs. proposed

Current — Monolith
  • Go client waits up to 120s for HTTP ack
  • 350–500MB baseline, all deps always loaded
  • CPU-bound NLP starves the async event loop
  • SQLite: single writer, no concurrent writes
  • New TCP connection to PM APIs per request
  • Scale = duplicate the entire process
Proposed — Event-Driven Workers
  • HTTP ack in < 5ms; processing is fully async
  • ~80MB per specialized worker process
  • Workers are pure async — no CPU event-loop blocking
  • PostgreSQL: concurrent writes, proper isolation
  • Pooled connections — 50–200ms faster per PM call
  • Scale trigger workers independently via NATS

Why NATS JetStream (not Kafka)

Kafka requires a JVM, ZooKeeper or KRaft, and carries a 512MB+ memory baseline. RabbitMQ adds a new runtime. NATS is a single ~20MB Go binary. JetStream gives persistence and at-least-once delivery. The Go gateway already has the NATS Go client available. NATS queue groups provide zero-config horizontal scaling: docker compose up --scale trigger-worker=4 automatically distributes messages across all instances with no sticky sessions.

Replace spaCy with LLM-only NLP

spaCy was necessary when LLM inference was slow and expensive. With Ollama running locally, a 3B parameter model parses a commit message in 200–400ms with better structured output than spaCy's entity extraction. Removing spaCy eliminates 50MB of model weight, the import overhead, and the CPU event-loop blocking. Since acking is now decoupled from processing via NATS, the developer never feels this latency anyway.

Connection pooling — the highest ROI fix available today

The current GitHub, GitLab, and Azure clients create a new aiohttp.ClientSession on each request, which creates a new TCP connection pool from scratch — adding 50–200ms per PM sync call due to TLS handshake overhead. The fix is three lines per client:

class GitHubClient:
    _session: aiohttp.ClientSession | None = None   # shared pool

    @classmethod
    async def get_session(cls) -> aiohttp.ClientSession:
        if cls._session is None or cls._session.closed:
            cls._session = aiohttp.ClientSession(
                connector=aiohttp.TCPConnector(limit=20, ttl_dns_cache=300)
            )
        return cls._session

This single change, requiring no architectural modification, cuts PM sync latency by 50–200ms per call. It is the highest ROI change available in the current codebase today.

13 Implementation Priorities

Ordered by impact-to-effort ratio.

1

Fix connection pooling in PM clients Do now — 1 day

~15 lines across three client files (GitHub, GitLab, Azure). Immediate 50–200ms latency reduction on every PM sync. Zero risk, zero architecture change. Demonstrable benchmark improvement. Ship this week.

2

Replace spaCy with LLM-only NLP Do now — 2 days

Remove the spaCy dependency. Route all text parsing through the existing LLM abstraction with a structured JSON prompt. Eliminates 50MB+ memory, removes CPU event-loop blocking, simplifies the dependency surface. The LLM already handles this in the fallback path — this makes it the primary path.

3

NATS JetStream + trigger worker process Sprint 1 — 1 week

Adds NATS (~20MB binary). Introduces trigger_worker/ as a separate Python process. The FastAPI server becomes a thin router. Trigger ack latency drops from up to 120s to under 5ms. Workers scale independently with --scale trigger-worker=N.

4

PostgreSQL + asyncpg as primary store Sprint 2 — 1 week

Migrate from SQLite. Use asyncpg in the trigger hot path, SQLAlchemy for migrations and admin queries. Add pgvector to replace ChromaDB. Enables concurrent writes, proper isolation, and vector similarity search without a separate embedding service.

5

OpenTelemetry export from runtime-narrative Sprint 3

Add an OTel exporter alongside existing JSON log output. Traces flow into Grafana Tempo, Jaeger, or DataDog. No application code changes — the instrumentation already exists. Enables distributed tracing across client and server in enterprise deployments.

6

Admin console Server-Sent Events Sprint 3

Replace 30-second HTMX polling on the stats panel with a persistent SSE endpoint. The server pushes updates when state changes. Browser-native, zero JS framework, eliminates polling overhead entirely.

7

Multi-tenancy + per-tenant LLM routing Future

Tenant isolation via workspace namespacing, per-tenant LLM provider configuration and rate limiting. Built on the existing workspace routing model — tenant ID is added to workspace config and the router dispatches accordingly. Configuration-layer change, not a re-architecture.

8

Kubernetes manifests + Helm chart Future

Package each component as separate Kubernetes deployments with HPA on trigger workers based on NATS consumer lag. The architecture is already correctly decomposed for this — this is an ops packaging step, not a code change.

14 Summary for Stakeholders

What exists today

DevTrack is a working, deployed, feature-complete developer automation platform. It monitors Git activity, applies AI enrichment, syncs work updates to four PM platforms, delivers notifications across five channels, and provides a web admin console with user management and a full audit log. All of this runs on a developer's machine with zero cloud dependency when Ollama is used.

Why the architecture is sound

The two-component model — Go client and Python server, HTTP-only boundary — is the correct separation of concerns. The Go binary is fast, portable, and trivially deployable. Python is where the AI ecosystem lives, and that is where Python genuinely wins. Neither component is trying to be the other. The boundary between them is explicit, versioned, and tested against a defined API contract.

What needs to change for enterprise scale

The core architectural pattern is correct. What needs to change is the deployment model, not the design. Adding a message queue between the gateway and the workers, moving from SQLite to PostgreSQL, and separating the monolith into specialized processes — these are execution-layer changes that do not require redesigning any feature that already works.

The one change that makes the biggest difference today

Fixing connection pooling in the PM platform clients. Three files. ~15 lines of code. 50–200ms latency reduction on every PM sync call. No architectural change. No risk. This is the change to make first, and it can ship this week.

🚀

DevTrack is not a prototype. It has production-quality config validation, graceful degradation for all optional dependencies, structured observability with LLM-powered failure diagnosis, HTTPS transport, scrypt-hashed authentication, a full web admin console, and a complete audit log. The scalability roadmap is an evolution of a working system — not a rescue of a broken one.
